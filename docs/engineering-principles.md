## 一、铁律 4 全文（裁定原文，逐字照录）

> **零技术债原则（运营者 2026-11-07 裁定）**：不为当下业务需求做 workaround。
> 解法必须循通用惯例/标准实践，且**为未来进来的协作者（含 agent）可读**——
> 他们只凭仓内材料就应能看懂逻辑。宁花时间花 token 彻底修复，不引入会漂移、
> 会分叉、需要口口相传的私有补丁。判定问句：「一个从未见过本项目的新 agent，
> 六个月后读到这段，能不能不看会话记录就懂？」不能=债。
>
> - 已知债型：复制体分叉（两份同源文件各自演化）、双正本+同步腿（本可单源）、
>   每处内联重复的兜底逻辑（本可抽公共件）、只在本会话语境里说得通的特判。
> - 债的处理：登记→重构卡（按漂移风险排序）→ 择窗清偿；清偿前新增改动必须
>   同步两处（债的冻结利息规则）。

## 二、判定问句（每个 PR / 每张施工卡自检用）

> **「一个从未见过本项目的新 agent，六个月后读到这段，能不能不看会话记录
> 就懂？」** 不能 = 债。

操作化三问（任一问不能，即按债处理）：

1. **单源问**：同一事实/逻辑在仓内有几个正本？>1 个 ⇒ 复制体分叉或双正本
   债，除非已有机器面对账（如 sha 钉桩）兜底。
2. **惯例问**：这个解法是通用惯例/标准实践，还是只为当下需求发明的私有
   补丁？后者 ⇒ workaround 债。
3. **可读问**：只读仓内文件（含注释、判据件、台账）能否理解为什么这么写？
   需要「当时会话里说过」才能懂的 ⇒ 债。

## 三、已知债型（铁律 4 列举四型 + 判定线索）

| 债型 | 形态 | 仓内判定线索（grep/结构信号） |
|---|---|---|
| 复制体分叉 | 两份同源文件各自演化 | 两文件 diff 从「n 处定点改」随时间扩大；一处的修复只落一边 |
| 双正本+同步腿 | 两个权威面 + 定时搬运脚本 | 存在 `*-sync.sh` 类同步腿；两件行数/内容稳定差几个版本 |
| 内联重复兜底 | 同一兜底逻辑每处手抄 | 同一注释块（如「三级克隆兜底」）出现在多个 workflow；commit message 出现「同款移植」 |
| 会话语境特判 | 只在本轮对话里说得通的 if/export | 注释引「2026-11-07 夜实测」「运营者口头」而无判据件坐标；env 特判散在作业 step 内 |

## 四、债的处理规则（铁律 4 第二节操作化）

1. **登记**：发现债 ⇒ 按债号顺号在 `计划/阶段欠账台账.md`（登记权威面）记行，
   写明 file:line 证据与漂移风险级（高/中/低）。债号顺号=接着台账最大编号
  往下排；派卡前置 = 先登记债行或换锚（占用闸对无行债号 fail-closed BLOCK，
   见 `.github/ISSUE_TEMPLATE/card.yml` 禁项 5）。
2. **重构卡**：按漂移风险排序开重构卡（标题带 `[技术债]`，卡面九项字段自包含，
   机读行块 `af-card/1.0` 齐备）。高风险债优先；不清偿前不派新施工放大它。
3. **择窗清偿**：重构方向=循惯例的正解（见各债行「归还方向」列），择窗施工；
   清偿=删债源而非加第二份适配层。
4. **冻结利息规则**：清偿前，对债面的新增改动**必须同步两处**（双正本）或
   **同步全部复制体**（分叉），并在 PR 自检清单勾选「无 workaround」项说明
   利息已付。禁止「只改一边、赌没人发现」——那就是让债增殖。

## 五、范例（好解法 vs workaround 对照 · 均取自本仓真实案例）

> 三条对照的共同点：**机器面可判、单源可循、注释自证**。新 agent 只读仓内
> 材料即可复核每一条（file:line 已给）。

### 范例 1 · 单源复用 vs 复制体分叉

- **好解法（单源）**：`factory-os` 的 PR 门剖面② bot-scrub 树扫，扫描内核
  **直接复用** `tools/mirror-disclose.sh` 内嵌 python 段的 `scan_text()` 纯函数
  ——gates.yml 用 AST 切出 `<<'PYEOF'` 段、只执行 `scan_text/scan_g13` 及其
  依赖闭包（`factory-os/.github/workflows/gates.yml:29-33` 头注自述；实现
  `tools/mirror-disclose.sh:270` `def scan_text`）。模式表改一处，门与树扫
  同源生效，零分叉。
- **workaround（复制体分叉，技术债清册 D-122）**：`planner-shadow-anolis.yml`
  以整文件复制 `planner.yml` 落库（commit `938ad57` 自述「以 main planner.yml
  （sha e5151313e54b）机械复制，四处定点改」）。此后两文件各自演化：
  planner.yml 增长到 3712 行（调查环 #110、factory_obs #108、实质门 #106），
  影子轨只落了三级克隆兜底（#112）与 fork 守卫（#114）——复制时的「4 处 diff」
  已扩为数十处，且**没有任一方知道对方改了什么**。新 agent 必须同时读两文件
  加 git log 才能判断一处改动该不该同步到影子轨。正解方向：`workflow_call`
  可复用工作流单源双用，或 CI 生成影子件（清册 `30-工件/技术债清册-20261107.md`
  D-122 行）。

### 范例 2 · 真源按需加载 vs 兜底逻辑内联重复

- **好解法（真源加载）**：`tools/factory-watch.py` 的发布面脱敏
  `scrub_public()` 不复制正则——经 `importlib.util.spec_from_file_location`
  按路径加载 `tools/stream-tailer.py` 的 `SCRUB_RULES` 真源
  （`tools/factory-watch.py:231-241`，注释原文「真源单一……importlib 按路径
  加载，不复制正则——P1-4 方向」）；真源缺失=显式降级拒绝写自由文本，
  而不是悄悄内联一份。
- **workaround（内联重复，技术债清册 D-124）**：三级克隆兜底链在
  `gates.yml:176-223`（L1 直连/L2 代理/L3 codeload）落了一遍，
  `planner-shadow-anolis.yml:512-598` 又手抄一遍——影子轨注释自认
  「gates.yml 检出步**同款移植**，只动本两步」（该文件 :512）。同一兜底逻辑
  两份各自演化：一处加 fail-closed 判红措辞、一处加 rm -rf 清残仓，差异只能
  靠人眼 diff 发现。正解方向：composite action 或仓内共享脚本单源
  （清册 D-124 行）。

### 范例 3 · 机器面对账兜底 vs 双正本+同步腿

- **好解法（不可免 duplication 时用机器面对账）**：`tools/ledger-sync.sh` 的
  同步是**只增不改 append-only 对账**——同步前后行数、既有行 sha 逐行比对、
  既有行前 5 格逐字节比对，不过即拒推（fail-closed）
  （`tools/ledger-sync.sh:15-17` 纪律①自述）。当两面临时不可避免时，用
  机器面把漂移钉住，比「相信人会记得同步」强。
- **workaround（双正本+同步腿，技术债清册 D-123）**：欠账台账存在两个正本——
  工作区 `计划/阶段欠账台账.md`（登记权威面，至 D-121）与 factory-os 仓
  `账本/阶段欠账台账.md`（规划环锚宇宙，2026-11-07 04 时止 D-68），中间靠
  `tools/ledger-sync.sh` 定时搬运（该脚本头注 :6-8 自述这一格局）。两件现值
  148 vs 145 行——**同步腿本身就是漂移证据**：任何时刻两本都可能差几个版本，
  而规划环只读仓内那本。正解方向：仓本为唯一正本，工作区侧改只读视图或
  彻底迁写（清册 D-123 行）。

## 六、执行面接线（本原则怎么被机器/流程强制）

- **PR 自检**：`.github/PULL_REQUEST_TEMPLATE.md` §5 自检清单第 5 项
  「无 workaround：解法循惯例、未来 agent 只凭仓内材料可懂（铁律 4）」。
- **派卡禁项**：`.github/ISSUE_TEMPLATE/card.yml` 禁项第 6 条（零技术债）——
  卡面九项字段之外，开工前先答判定问句；不能 = 先登记债号再开工。
- **占用闸**：债号顺号机检 `tools/dispatch-occupancy-check.py`（三面：台账/
  登记/在飞；无行债号 fail-closed）——债不登记就没有卡，卡不登记就派不出。
- **判官路径红线不变**：本原则**不**放松判据/判官件零改动纪律
  （`docs/judge-paths.md`）：清偿技术债同样不许顺手改门；要改判官路径只有
  运营者裁决正路。
